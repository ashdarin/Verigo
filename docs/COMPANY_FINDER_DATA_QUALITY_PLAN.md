# Company Finder 数据质量与展示方案

## 产品决策

Company Finder 应当是有条件的公司发现工具，不是 3,580 万条原始记录的公开目录。

- 原始目录仅作候选索引和追溯数据，不直接展示给普通用户。
- 用户必须输入公司名、域名、关键词，或选择至少一个有意义的筛选条件。
- 单次搜索最多向用户暴露 100 家公司，不提供对全库的无限翻页。
- 默认只展示已确认活跃或近期有公开证据的公司。
- LinkedIn 页面存在只是一项证据，不能单独证明公司仍在经营。
- 只有对接可信的官方工商数据后才可以标记“已注销”；官网失效只能标记为“当前无法确认”或“已停止展示”。

## Hunter.io 可借鉴的做法

Hunter Discover 采用“搜索或筛选 -> 有界候选集 -> Domain Search / Enrichment”的流程，而不是默认列出整个数据库。它的数据展示还包含公开来源、首次/最后发现时间、当前是否仍在来源页，并对近期核验结果和其他记录区分展示。当公开证据消失时，记录会进入移除状态；缺少公开来源的联系人/公司数据不会无限期保留。

## 数据分层

### 1. Raw Catalogue

现有 DuckDB/Parquet 保持为只读原始候选库。它负责快速找出可能匹配的公司，不承诺公司当前仍活跃。

### 2. Vitality Index

单独保存可变的质量与活跃性数据，不回写原始目录。建议最小字段：

- `company_id`, `domain`, `normalized_name`
- `dns_status`, `http_status`, `final_url`, `redirect_domain`
- `page_title`, `is_parked`, `identity_score`
- `last_checked_at`, `last_public_evidence_at`, `next_check_at`
- `consecutive_failures`, `company_state`, `confidence`
- `evidence` JSON，记录来源、发现时间和判定原因

索引在 Company Finder 专用服务侧维护，避免每次搜索跨 SSH 隧道反复读写上海 PostgreSQL。首期可使用 SQLite WAL 存储已核验子集，定时备份；当多实例扩容时再迁移到独立 PostgreSQL。

### 3. Enrichment

用户选择公司后，先复核域名与公司身份，再进入 Domain Search、联系人发现或邮箱验证。联系人结果不应与未核验的原始公司记录直接绑定。

## 状态模型

| 状态 | 判定 | 默认展示 |
| --- | --- | --- |
| `active_verified` | DNS/HTTPS 可达，网站内容与公司名或可信证据一致，30 天内复核 | 是 |
| `recently_observed` | 90 天内有有效证据，本次为超时或可恢复故障 | 是，标明最后核验时间 |
| `uncertain` | 只有历史/LinkedIn 记录，缺少当前官网证据，或身份匹配不足 | 否，仅管理员可查 |
| `inactive` | NXDOMAIN、停放/出售页、跳转到无关主体，或多次间隔复核失败 | 否 |

## 核验流程

1. 原始索引根据搜索意图取回最多 100 个候选。
2. 先合并域名和 LinkedIn slug 一致的重复实体。
3. 查询 Vitality Index，直接使用未过期的核验结果。
4. 对未核验或已过期候选异步执行 DNS、TLS、HTTP 重定向、停放页和身份匹配检查。
5. 只把 `active_verified` 与 `recently_observed` 排入普通用户结果；未完成的候选留在队列中，前端短轮询一次获取新增结果。
6. 详情页展示“最后核验时间 + 信心等级 + 证据来源”，不展示没有根据的确定性结论。

## 调度与退役

- 活跃公司每 30 天复核。
- 近期有证据但本次失败的公司，分别在 24 小时、3 天、7 天复核，避免把短暂网络故障当成停业。
- NXDOMAIN、停放页或身份明显不匹配的记录立即停止对普通用户展示。
- 连续多次失败且 180 天没有新的公开证据时，进入退役状态；原始记录仍保留用于审计。

## 前端展示

- 首屏是搜索和筛选器，不自动加载“第一页公司”。
- 结果显示公司名、经规范化的域名、国家/地区、行业、规模、核验状态和最后核验时间。
- LinkedIn 使用图标按钮，它是外部证据链接，不是活跃认证标识。
- 主操作是“查找联系人”或“查看公司详情”，将发现结果导入 Verigo 现有的 Domain Search 流程。
- 管理员可以切换“已核验 / 待确认 / 已隐藏”视图，普通用户不看原始状态。

## 实施阶段

1. **P0 查询可用性**：移除关键词全库排序，名称优先、域名补充，保证搜索不超时。
2. **P1 展示门槛**：必须有搜索条件，最多 100 条，普通用户不显示缺少官网的记录。
3. **P2 活跃性索引**：实现核验队列、状态表、缓存与调度，先预热搜索日志中的高频公司和主要市场。
4. **P3 用户产品化**：将公司发现从管理员页面迁到独立页面，接入详情页、证据、Domain Search 和使用量统计。

## 当前进度（2026-08-16）

- **P0 已上线**：关键词查询改为公司名优先、域名补充的有界检索，不再对全库匹配结果排序。
- **P1 已上线**：搜索必须带公司关键词或有意义筛选，默认仅查带官网的记录，且最多可查看 100 家候选公司。
- **P2 已完成并转为公开门槛**：Company Finder 专用节点使用 SQLite WAL 缓存活跃性证据，由独立的低优先级 Worker 以 2 个并发进行 DNS/HTTP/停放页/身份匹配检查。它的 CPU 上限为 40%、内存上限为 192 MB，与查询服务和邮箱验证 Worker 隔离。普通用户搜索只接收 `active_verified` 和 `recently_observed`，`uncertain`、`inactive` 及尚未完成检查的候选不会直接展示。
- **P3 已上线**：新增登录且已验证邮箱用户专用的 `/app/company-finder` 页面和 `/api/company-finder/search`、`/api/company-finder/facets/{facet}` 接口。页面支持公司关键词、国家/地区、行业、规模筛选，提供官网入口，并可将域名交给现有企业邮箱查找流程；管理员原有 Company Catalog 保持不变。
- **P4 已上线**：新增 `/api/company-finder/companies/{company_id}` 详情接口和 Company Finder 详情抽屉。详情接口在专用目录服务侧再次执行活跃性门槛，只返回 `active_verified`、`recently_observed` 记录；`uncertain`、`inactive`、未完成检查或不存在的记录统一返回 404。详情展示规范化公司资料、最近核验时间、可信度、公开证据类型和可读说明，并保留官网、LinkedIn 与企业邮箱查找入口。SMTP 结果文案未改动。
- **P5 已实现**：详情打开、官网访问、LinkedIn 访问和进入企业邮箱查找四类动作通过 `/api/company-finder/analytics` 聚合。请求只允许上报固定事件枚举，不接收公司 ID、名称、域名、邮箱或目录内容。PostgreSQL 仅保存按日计数和按“日期 + 事件”变化的 HMAC 用户散列；管理后台显示最近 14 天聚合，匿名去重行保留 45 天后由 retention 清理。埋点使用非阻塞 `keepalive` 请求，失败不影响外链跳转和页面操作。
- **P6 已实现**：公开证据拆分为官网法律信息、官网标题、官网正文、域名品牌和历史官网证据，并保存强/中等级、证据发现时间和适用市场。首批市场法律标识覆盖德国、澳大利亚、中国、比利时、阿根廷、阿尔巴尼亚、英国、法国、意大利、西班牙、荷兰、日本、韩国、印度、巴西和墨西哥等市场。只有身份匹配同时成立时，法律标识才会增强证据，单独出现登记词不会让公司通过公开门槛。
- **P6 复核调度**：用户当前搜索产生的候选优先级最高；历史证据和 `recently_observed` 先于普通 `active_verified` 到期复核，`uncertain` 与 `inactive` 在后。主要市场只获得小幅同级提升，不改变公开门槛。旧的公开记录由原有 2 并发低优先级 Worker 渐进复核；新规则第一次得出“身份不足”时保留 24 小时复核窗口，第二次仍不足才停止展示。一次性回填只把原目录的国家字段写入 724 条独立活跃度记录，并只重新安排可能形成市场法律证据的公开记录，不复制公司目录内容。
- **生产验收（2026-08-16）**：`/api/health` 返回 `status=ok`、`database=ok`；Web、worker API、Company Finder SSH 隧道、EC2 目录服务和活跃度 Worker 均为 active。专用目录健康统计为 389 条 `active_verified`、2 条 `inactive`、333 条 `uncertain`，`queued=0`、`checking=0`。公开搜索返回的样本详情均为 HTTP 200，并包含官网公开证据。上海应用发布不会自动更新隧道后的 EC2 目录服务；后续发布必须同步 `deploy/company-finder-service.py` 与 `deploy/company_vitality.py`，再重启 `company-finder.service` 并做详情回归。
- **P6 生产验收（2026-08-16）**：724 条活跃度记录的国家字段已全部回填，渐进复核和市场复核队列均清空。公开结果保持 389 条，其中 `active_verified=350`、`recently_observed=39`；证据分布为官网法律信息 48、官网标题 226、官网正文 76、域名品牌 38、等待可恢复故障后复核的历史证据 1。实际详情已返回证据种类、来源、强度、市场和发现时间。Worker 始终为 2 并发、`CPUQuota=40%`、`Nice=10`，复核期间内存低于 192 MB 上限；Web、worker API、Company Finder 隧道、目录服务及活跃度 Worker 均为 active。
- **P7 已实现**：Company Finder 专用节点按 UTC 日期聚合复核次数、最终状态、证据分类变化、公开/隐藏转换、首次排队等待和网站检查耗时。聚合表每天只有一行，结果落库时在原 SQLite 事务中执行一次常数级 UPSERT；不增加事件流水，不保存公司 ID、名称、域名、邮箱或页面内容。14 天报告通过带服务令牌的 `/vitality/report` 提供给上海应用，并由仅管理员可访问的 `/api/admin/company-catalog/quality` 代理。
- **P7 管理端**：公司目录筛选区新增无嵌套卡片的质量观测信息带，显示 14 天复核量、当前公开数量、公开结果净变化、平均排队时间、平均检查时间、每日趋势和当前证据分布。桌面 1440px 与移动 390px 的 Playwright 回归均无页面横向溢出，移动端图表只保留首尾日期以避免刻度截断。
- **P7 性能与隐私验收**：加入来源隔离后的本地 500 次连续事务基准中，包含聚合写入的 `complete()` 平均约 1.8ms，14 天报告平均约 4.1ms。报告契约测试确认不含测试公司的 ID、名称或域名；报告接口要求私有服务令牌，上海代理要求管理员身份。该链路只接触 Company Finder 专用 SQLite 与管理员页面，不进入 PostgreSQL 邮箱任务表，也不修改邮箱验证 Worker 或 SMTP 结果文案。
- **P7 观测采样已实现**：专用采样器前 24 小时以每天 5,000 家预热；队列低于 500、网站检查直方图至少积累 500 个样本、且 P95 不超过 8 秒后自动提升为每天 10,000 家，配置硬上限为每天 15,000 家。systemd timer 每 15 分钟释放一个小批次，默认预热批次约 53 家、稳定批次约 105 家，不在午夜一次性堆积任务。
- **采样组成与抢占**：每批目标最多包含 15% `uncertain`、10% 公开记录、5% `inactive` 或历史证据，其余名额从未检查的原始目录补足。原始目录通过六个确定性随机 `rowid` 区段读取，并给 20% 名额增加国家、行业和规模覆盖，不执行 `ORDER BY RANDOM()`；生产目录读取 200 条候选实测约 11–40ms。抽样优先级固定为 200，低于用户搜索和所有正常到期复核；总队列达到 500 时采样器暂停。
- **来源隔离**：队列与日报分别标识 `user_search`、`scheduled_refresh`、`daily_sample`。管理员报告同时显示自然复核、抽样复核、当日计划和已安排数量；各来源分别计算排队和网站检查耗时。报告仍只有每日聚合，不暴露采样公司的 ID、名称、域名或邮箱。采样器 CPU 上限为 20%、内存上限为 320MB、`Nice=15`，网站探针继续由原 2 并发、CPU 40%、内存 192MB 的低优先级 Worker 执行。
- **长尾耗时观测**：排队等待和网站检查耗时写入固定上界桶，仅按 UTC 日期、任务来源、指标和桶上界累计计数；不保存单次事件或公司标识。报告从桶计数估算 P95/P99，历史日期在没有桶数据时明确返回空分位数，不用平均值伪造。桶表每天最多为 `3 来源 × 2 指标 × 13 桶` 的有界规模。
- **抽样升档门槛**：首 24 小时保持 5,000 条/日。此后只有队列少于 500、当日抽样网站检查至少积累 500 个样本、且检查 P95 不超过 8 秒时，才升至 10,000 条/日；任一条件不满足就继续以 5,000 条/日运行。门槛均可通过环境变量调整，但硬上限仍为 15,000 条/日。
- 管理员结果现在显示“待核验、近期可确认、近期有记录、暂未确认、已停止展示”状态；普通用户只看到有近期公开活跃证据的结果。
- 单次 NXDOMAIN 只标为“暂未确认”并在 24 小时后复查，避免 DNS 故障造成批量误隐藏；连续两次才停止对普通用户展示。

### 下一阶段（P8 决策门槛）

- P7 连续积累至少 14 天后，比较“详情 -> 官网 / LinkedIn / 企业邮箱查找”的动作比例，再决定详情字段和排序调整；不基于低样本数据提前改变检索逻辑。
- 同期观察证据类型分布、公开结果净变化、队列等待和检查耗时。只有当特定市场持续缺少官网证据且用户搜索量足够时，才评估接入该市场的官方工商登记源。
- 官方源必须单独标识来源、适用市场和发现时间，不能把第三方目录记录包装成注册状态；接入前还要确定许可、缓存期限、请求限额和失效处理。

## 验收标准

- Company Finder 查询 p95 小于 1 秒，p99 小于 3 秒。
- 普通用户接口返回的每条可展示记录都包含状态、最后核验时间和核验原因；详情接口额外返回公开证据类型、可信度和可读说明。
- 任意查询最多暴露 100 条，空条件不返回全库列表。
- 域名停放、NXDOMAIN 或身份不匹配的公司不进入普通用户结果。
- 未登录或未验证邮箱的用户访问 Company Finder API 返回 401/403，不能绕过产品权限读取目录。
- 核验任务、搜索和邮箱验证 Worker 之间资源隔离，公司核验不影响邮箱验证速率。
